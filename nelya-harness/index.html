Nelya Sign-up Harness

An AI agent that takes a contractor from a first text message to a live AI front desk: it qualifies them, collects their details and payment, sets up their phone number and launches the service, all by text. The model handles the conversation. Code enforces every rule.

Built & tested · staging deploy next Claude Agent SDK Model Context Protocol (MCP) Cloudflare Workers · Containers · D1 Twilio Stripe

The problem

Nelya is Divoit's missed-call text-back service for contractors. When a plumber or roofer can't pick up, Nelya texts the caller within seconds so the lead isn't lost. The product worked, but signing up a contractor was manual. Someone had to collect their details, send a payment link, buy and configure a phone number, walk them through call forwarding on their carrier, and agree the wording customers would see.

That is a dozen steps over several days, with money and phone numbers involved. It's a good job for an agent, as long as the agent can't take a step out of order, spend money nobody approved, or tell a contractor something untrue.

The approach: the model talks, the code decides

The main design decision: no business rule lives in the prompt. The agent can only act through ten narrow tools. Each tool call goes back to the Worker, which checks it against a state machine and the sign-up's saved data before anything happens. If the model tries something it shouldn't, the tool refuses with an explanation, and the refusal is logged.

The agent container holds no keys. Its tool calls and model calls both go through the Worker using a short-lived run token.

Design decisions

1. A state machine owns the journey

Each sign-up moves through fixed stages: started → details → form_sent → form_done → link_sent → paid → number_pending → number_ready → forwarding_sent → forwarding_ok → live, plus needs_faiz and closed. The allowed next stages are listed in code, and every update is a versioned compare-and-set, so two events arriving at once can't both move the same sign-up. The agent can't send a payment link before the secure form is done, or forwarding steps before a number exists. It doesn't have to remember these rules, because it can't break them.

2. Narrow tools, enforced by an allowlist

The agent gets ten purpose-built tools (get_signup, save_details, send_text, create_payment_link, propose_number, and so on), each with a typed schema. Every other capability is denied in canUseTool, including the SDK's built-in file and shell tools. During the build I found that listing tools in allowedTools silently skips the canUseTool check, so the design uses an empty tools list plus the allowlist callback.

3. A human approves anything that costs money

The agent can propose a phone number. Only the business owner's YES, sent by text, makes the Worker buy it. Limits sit in code too: at most two texts to the contractor per turn, at most three escalations to a human per day, and every text checked for length and content.

4. No secrets in the agent

The container never sees an API key. The Worker mints a short-lived signed run token for each run. The agent uses it to call the tool endpoint and a model proxy, and the proxy adds the real key on the Worker side. If the container were compromised, it would hold nothing worth stealing.

5. Observable by default

Every tool call is written to the database with its duration and, when refused, the reason. A private admin dashboard shows sign-ups by stage, the tool-call log and refusals. That's how I check the guardrails are doing their job, not just that the happy path works.

6. Safe to ship

The whole feature is behind a flag and off by default. It plugs into the existing text-line Worker through two small hooks, and the existing Nelya regression suite passes with the harness both off and on.

Measured, not guessed

Before building the full harness, I ran a one-day spike to check the riskiest assumption: could the Claude Agent SDK, running in a Cloudflare Container, answer a text fast enough? The target was a reply within 60 seconds. A GitHub Actions workflow deployed a throwaway copy, measured 8 cold and warm runs, saved the results and deleted it.

How it was built

I ran this the way I'd run an enterprise program, with an AI team. An Architect agent wrote the requirements, high-level and low-level designs. A Tester agent reviewed the design and found eleven issues before any code was written. A Developer agent built it test-first. I owned the scope, the trade-offs, the approvals and the go/no-go at each gate. The program discipline from my enterprise years is what kept AI-written code shippable.

What's next

  • Staging deploy: a separate Worker and database, Twilio in test mode, the real agent and dummy data, followed by a Tester agent pass.
  • Pilot with one contractor, then production.
  • An eval harness: a fixed set of sign-up conversations scored automatically on every prompt or model change, so improvements are measured instead of guessed.

The source is private because it's part of a live commercial product. I'm happy to walk through the code, the design documents and the test results in an interview.
